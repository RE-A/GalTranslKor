비주얼 노벨 번역**이다. 유려해 보여도 부정·행위자·호칭이 바뀌거나 정보를 덧붙이면 품질 저하다.

이미 한국어 지침, 용어집, 캐릭터 사전, 이전 번역과 이후 원문 문맥, 재시도,
자동 오류 리포트가 있다. 먼저 이 기능에 들어가는 정보를 정리하고 품질 비교 기준을 마련하는 것을 추천한다.
효과가 확인된 개선부터 추가하고, 장면 기억이나 전면 재검토는 비용 대비 효과를 측정한 후 결정한다.

### Q1. 평가 기준부터 만들기

- [ ] 직접 작성한 합성 장면 8~12개, 총 100~200항목을 준비한다. 대사·지문·독백을 섞고
  존대 전환, 생략된 주어, 부정·이중부정, 수수 표현, 동음 이름, 언어유희, 장면 전환을 포함한다.
  한두 문장만으로는 드러나지 않는 말투 변화와 배치 경계 오류도 넣는다.
- [ ] 각 항목에 정답 문자열 하나 대신 반드시 보존할 의미, 허용 번역 예, 금지 오역과 근거를 적는다.
  개발에 쓰는 예시와 최종 평가용 장면을 나누고, 평가용 정답을 프롬프트에 넣지 않는다.
- [ ] 의미 정확성, 한국어 자연스러움, 인물 말투·관계, 용어 일관성을 각각 0~4점으로 평가한다.
  누락·행위자 반전·부정 반전·제어코드 손상은 별도로 집계해 평균 점수에 가려지지 않게 한다.
- [ ] 동일 원문에 대한 기존/개선 출력을 A/B 이름을 가려 비교하고 동률도 허용한다.
  평가자는 원문과 필요한 장면 문맥을 함께 본다. 모델 평가는 참고로만 사용하고 사람의 확인을 기록한다.

완료 기준: 평가 데이터·채점 설명·실험 기록 양식이 재사용 가능하고, 로컬 Windows에서
기준 설정의 점수와 오류 유형별 빈도를 확보한다. Cloud에서는 데이터·집계 흐름과 Mock만 검증한다.
BLEU 같은 단일 문자열 유사도 점수나 자동 오류 0건으로 문학적 품질을 판정하지 않는다.

### Q2. 캐릭터 말투를 상대와 상황에 연결하기

- [ ] 기존 `characters.yaml`의 `speech`, `honorifics`, `relationships`에

### Q5. 문맥은 양보다 경계와 관련성을 개선하기

- [ ] 질문과 응답, 한 문장의 여러 줄을 가능한 한 함께 해석할 수 있도록 배치 구성 후보를 검토한다.
  모델 입력의 묶음과 원본 출력의 행·ID는 구분하며, 출력 항목을 합치거나 순서를 바꾸지 않는다.
- [ ] 명시된 장면 전환·루트·시간대 경계와 대사/지문/독백 정보를 활용할 수 있는지 확인한다.
  파일 순서만으로 다른 루트의 문맥을 이어 붙이지 않는다. 경계 정보가 없으면 추정의 한계를 기록한다.
- [ ] 이후 원문은 지시어·생략 해석에만 사용하고 다음 줄의 내용이나 뒤에서 밝혀질 사실을
  현재 번역문에 앞당겨 추가하지 않는 평가 사례를 만든다.
- [ ] 관련 인물·용어·최근 발화의 중요도를 고려하되, 기존 문맥 제거 규칙과 비교해 개선 여부를 측정한다.
  `maxPromptChars`는 문자 예산이고 `numCtx`는 토큰 창이다. 고정 글자/토큰 비율을 보장값으로 쓰지 않는다.

완료 기준: 같은 입력 예산에서 배치 경계의 지시어·화자 오류가 줄고, 분기 혼입과 정보 선행이 없다.
실제 토큰 사용량과 출력 여유·속도는 로컬 Windows에서 확인한다.

### Q6. 원문을 보는 선택적 검토

  검토 입력에 일본어 원문, 초벌 번역, 확정 용어·관계 정보를 함께 제공한다.
- [ ] 누락·추가, 부정·행위자·수량, 이름·호칭을 먼저 점검하고 이후 문체를 다듬는다.
  변경 위치·이유를 남기며 '수정 없음'도 정상 결과로 인정한다.
- [ ] 수정 결과에도 ID·제어코드·줄바꿈 검증을 적용하고, 검증 실패 시 기존 번역을 보존한다.
  문체만 더 매끄러운 의미 오역을 자동 채택하지 않도록 검토 단계의 수용 기준을 정한다.
- [ ] 경고만 보면 놓치는 오류가 있으므로 정상 판정 항목 일부도 표본 검토한다.
  같은 모델의 자기 검토를 독립적인 정답으로 취급하지 않고, 다른 모델 검토도 실제 효과를 비교한다.

완료 기준: 사람이 확인한 순개선 건수(고친 오류와 새로 만든 오류를 모두 기록)와
추가 호출·소요 시간을 비교해 이득이 있는 범위를 정한다. 재검토 횟수에는 상한을 둔다.

### Q7. 한국어 오류 경고를 정교화하기

- [ ] 용어 표기 변화, 상대별 존대 불일치, 숫자·부정·열거 누락 의심을 검토 후보로 표시한다.

- [ ] 정상적인 짧은 대답, 원문 자체의 거절·번역 관련 대사, 허용된 외국어를 포함한 반례를 마련한다.
  현재 길이·거절 감지의 오탐과 미탐을 실제 출력에서 측정한다.
- [ ] 구조 손상과 언어적 의심을 구분하고, 불확실한 규칙은 우선 경고로 평가한다.
  오탐 때문에 정상 문장을 반복 재번역하거나 말투를 바꾸지 않도록 한다.

완료 기준: 오류 유형별 적중률·놓친 오류·오탐 수를 기록한다. 문장 수 대비 전체 정확도만으로 판단하지 않는다.
형태소 분석기 등 새 의존성은 단순 규칙 대비 필요한 이득이 확인될 때 검토한다.

### Q8. 모델과 설정을 한 변수씩 비교하기 — 로컬 Windows 전용

- [ ] 모델명·버전/식별자, 양자화, Ollama 버전, 하드웨어, API 방식, 지침·사전 버전을 기록한다.
  모델 크기나 번역 특화 표방만으로 한국어 품질을 단정하지 않는다.
- [ ] 기준 모델을 고정하고 배치, 이전/이후 문맥, 온도 등을 한 항목씩 비교한다.
  예제의 배치 5·이전 8·이후 4·온도 0.2는 출발점으로만 사용한다.
- [ ] 다음으로 다른 모델·양자화를 같은 평가 세트에서 비교한다. 작은 모델의 여유 문맥이
  큰 모델의 짧은 문맥보다 유리한지도 품질·속도·메모리를 함께 보고 판단한다.
- [ ] 각 조건은 별도 캐시/출력에서 실행하고 생성된 결과를 사람이 평가한다.
  가능한 조건은 반복 실행하며 낮은 온도가 오역을 없애거나 완전한 재현성을 보장한다고 가정하지 않는다.

완료 기준: Q1 점수·중대 오류, 처리 시간, 실패/재시도, 실제 토큰과 GPU/메모리 결과를 함께 기록한다.
기존 `benchmark_ollama_ko.py`의 성능 집계를 활용하되 자동 리포트를 언어 품질 점수로 부르지 않는다.
현재 사용자에게 PC 실행이나 모델 제공을 요청하는 과제가 아니다.

### Q9. 장면 기억은 근거와 범위를 함께 보관하기

- [ ] Q5 이후에도 최근 문맥 밖에서 발생하는 오류가 반복되는 경우에만 검토한다.
  이미 나온 사실·현재 관계·호칭 변화·미확정 지칭을 원문 위치와 함께 짧게 유지하는 방식을 비교한다.
- [ ] 번역문을 다시 요약하는 방식으로 오역이 사실처럼 굳어지지 않게 원문 근거를 둔다.
  미확정 정보는 추측으로 확정하지 않고, 인물의 믿음과 실제 사건을 구별한다.
- [ ] 장면·루트별 격리, 분량 상한, 중단 후 복원, 원문·사전·번역 수정 시 재생성 범위를 정한다.
  앞부분 교정이 뒷부분 캐시와 기억에 미치는 영향도 평가한다.

완료 기준: 긴 합성 장면에서 최근 문맥만 쓸 때보다 일관성이 좋아지고 잘못된 기억의 전파가 통제된다.
기억이 차지하는 입력 예산과 추가 호출 비용까지 Q8과 같은 기준으로 비교한다.

### Q10. 확인된 교정 사례만 재사용하기

- [ ] 사람이 확정한 원문·번역·문맥·교정 이유를 실행 캐시와 구분해 관리하는 방식을 검토한다.
  캐시 성공은 구조 검증 성공일 뿐, 의미까지 검수됐다는 뜻은 아니다.
- [ ] 비슷한 표현의 사례는 작품·화자·상대·의미가 맞을 때만 참고한다.
  동일 원문이라도 관계와 장면이 다르면 같은 번역을 강제하지 않는다.
- [ ] 평가용 정답 유출, 다른 작품 이름 혼입, 오래된 용어 표기 재사용을 방지하는 기준을 마련한다.

완료 기준: 이미 교정했던 유형의 재발이 줄고 새로운 문맥에 잘못 적용되는 비율도 기록된다.
실제 게임 원문·교정 데이터·번역 출력·캐시는 Git에 커밋하지 않는다.

## 추천 착수 순서와 검증 경계

1. Q1 평가 기준을 준비하고 Q2·Q3으로 기존 사전 정보를 정리한다.
2. 로컬 Windows 검증이 가능해지면 기준 결과를 확보하고 Q4·Q8을 비교한다.
3. 오류 분석에서 문맥 부족이 확인되면 Q5, 검토 효과가 예상되면 Q6·Q7을 진행한다.
4. 긴 장면의 잔여 오류와 반복 교정 비용이 확인될 때 Q9·Q10을 검토한다.

Cloud에서 향후 가능한 작업은 합성 데이터 작성과 문맥 선택·보존·검증·캐시 의존성의 Mock 테스트다.
실제 모델을 통한 품질·성능 판정은 로컬 Windows에서만 수행한다. 현재는 문서 검토만 완료했다.
항목을 실제로 시작할 때 사용자 요청 범위를 확인하고, 측정 결과가 있어야 완료 표시한다.
구현 난도가 높다는 이유로 이미 있는 기능을 중복 개발하거나 모든 후보를 한 번에 도입하지 않는다.
